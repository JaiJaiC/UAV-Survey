Guanzheng Wang 的强化学习仿真器选择图谱

覆盖 2021 硕士论文 → 2026 两篇期刊论文，共 6 个作品。回答四个问题：他用什么仿真器 · 为什么 · 好在哪里 · 有什么问题。每一条结论都标注了来源作品编号，可直接跳转核对。

0. 结论先行（先看这 6 句）

① 他不用"一个万能仿真器"，而是按传感器需要什么保真度来选 几何感知（LiDAR）→ Stage（2.5D，最快）；光度感知（事件相机）→ AirSim + Unreal Engine（最贵）；飞控在环验证 → Gazebo + PX4 SITL；固定翼 6-DOF → JSBSim（纯动力学、可关渲染）。这条判据是全篇最有价值的一条经验。
② 训练侧永远选"便宜的那个"，验证侧才用"贵的那个" Stage（训练）→ Gazebo（验证）、自建 6-DOF（训练/验证同环境）、JSBSim（训练，渲染可关）。他几乎从不在高保真仿真器里训练——这是延续六年的稳定习惯。
③ 全部 6 个作品都没有用 GPU 批量仿真（Isaac Gym/Lab、MJX、Newton） 清一色 CPU + 多进程（mpi4py 12 进程 / SB3 SubprocVecEnv 16 进程）。这是团队路径依赖的清晰指纹，也是他与 2024 年后主流 UAV-RL 工作最大的技术代差。
④ 算法栈极其统一：Gym + Stable-Baselines3 + PPO，六年没换 6201（A2C/TD3/SAC/PPO 对照）、6202（PPO 默认超参）、6203（PPO）、6205（PPO）、6204（PPO）、6206（策略梯度类）。换的是仿真器和任务定义，不是学习算法。
⑤ 最大的系统性缺陷：训练域与验证域的"物理落差"从未被量化 Stage 是运动学质点，Gazebo 是带姿态动力学的真实旋翼，自建仿真是理想积分。他从未做过"同一策略在同一场景、两个仿真器中各跑一次"的对照——而这个数字恰恰是 sim-to-real 论文最该有的一张表。
⑥ 真机实验只有一次（2021 硕士论文），之后全部停在仿真 2021 年有 PX4 SITL + 真机多机飞行；2022 后全部为纯仿真（6202 只到 SITL）。对一位做"可靠性/安全性"的团队，这是解释力上的明显断点。

3. 为什么这么选（逐类拆解）

3.1 为什么训练用 Stage

  • 任务的下界就是 2D：观测是单层 2D LiDAR，动作是 $[v,\omega]$，运动学是单轨——用 3D 仿真器等于为用不到的自由度付钱。
  • 吞吐：Stage 用 2D 占据栅格 + 射线投射，无 3D 渲染、无刚体动力学积分，headless 进程内即可跑；10 万回合（6202）或 4×105 episodes（6205 的横轴到 400000）在桌面 CPU 上可完成。
  • 随机化便宜：障碍位置随机生成、场景批量实例，对课程学习（6205 两阶段）特别友好。
  • 与 ROS 生态兼容：stage_ros 是 ROS 官方包，与后续验证栈的接口一致。

3.2 为什么验证必须换成 Gazebo + PX4 SITL

  • 补上 Stage 缺的三件事：真实旋翼动力学（PX4 姿态/位置环）、传感器物理、场景真实感。
  • 把策略接到真实飞控栈：速度指令 → MAVROS → PX4 → 电机。这条链路与真机完全一致，是 sim-to-real 最有信息量的中间一步。
  • 有现成开源工程：XTDrone（作者团队）把 Gazebo/PX4/ROS/MAVROS 的胶水都写好了，边际成本极低。

3.3 为什么固定翼用 JSBSim 而不是 Isaac/MuJoCo

  • 气动表是硬需求：X8 的系数来自风洞 + CFD，JSBSim 的 .xml 格式就是为气动表设计的；换到 MuJoCo/PyBullet 要自己重写插值。
  • 它是"纯动力学"：无渲染、无 ROS、无场景——因此极快，且容易塞进 Gym 循环。
  • GPU 批量在这里用不上：固定翼回合长（1200 步）、状态维度低，瓶颈是 CPU 单线程积分；16 进程已能吃满桌面多核。
  • 与渲染解耦：Unreal 只是"可选显示器"（论文原话：训练时可禁用渲染引擎）。

3.4 为什么事件相机必须 AirSim/UE

  • 事件 = 亮度变化的函数，所以需要真实的 PBR 材质、全局光照、动态阴影——Gazebo 的 OGRE 与 Stage 的 2D 栅格都给不了。
  • 有现成插件：AirSim 的 event-sim 用两张连续 RGB 算事件，分辨率与 TOL 可调。
  • 碰撞回调可直接当奖励：省去自写碰撞查询。
把四条理由抽象成一句判据 仿真器的保真度只需覆盖"你的观测函数所依赖的那部分物理"。观测 = 距离 → 只需几何；观测 = 亮度 → 需要光度；观测 = 气动状态 → 需要 6-DOF 气动表；动作 = 速度指令 → 需要飞控在环。

4. 好在哪里（可以直接抄的 6 条经验）

经验 1

轻训练 / 重验证

训练用便宜仿真器把策略学出来，验证用高保真仿真器（甚至真机）验收。中间只传一份权重。6202 是最干净的实例。

经验 2

物理与渲染解耦

JSBSim 只算动力学，Unreal 只画图，而且训练时可关渲染。这一条几乎可以无脑套用到任何"高保真 + RL"场景。

经验 3

Gym 封装 + SB3 向量化

gym.make(...) + SubprocVecEnv(16)，换算法只改一行。这是"四种算法严格对照"能实现的前提。

经验 4

仿真器跟着传感器走

同一个团队，三种传感器对应三种仿真器。不屈从"团队习惯"，只服从"观测函数需要什么"。

经验 5

飞控在环是性价比拐点

PX4 SITL 带来的可信度提升，远大于换一个更好的物理引擎——因为执行链路与真机同构。

经验 6

代码即论文

6201 开源 OpenFlight、6203 给了代码与数据集地址、6202 依赖开源的 XTDrone。把关键数字（16 进程 / 30 Hz / x8.xml）变成可核对的事实。

5. 有什么问题（按严重程度排序）

#问题证据（出自哪篇）严重度
1 训练域 ↔ 验证域的物理落差从未被量化：Stage（运动学）→ Gazebo（动力学），性能变化混入了"泛化"的结论里；没有"同场景双仿真器"对照 6202（最典型）、6206（Stage + Gazebo） ★★★★★
2 真机实验只有 2021 年一次，之后六年全部停在仿真；对一个做"可靠性/安全"的团队这是解释力断点 6202/6203/6204/6205/6201 全部无真机 ★★★★★
3 无域随机化（DR）：气动系数、质量、延迟、传感器噪声均未扰动；6201 甚至明确说策略是"为 X8 定制" 6201、6202、6205 ★★★★★
4 仿真器完全不透明：6204 无名称、无版本、无代码、无时间步长 6204 ★★★★
5 训练 = 验证同环境：6203、6204 明确写"验证设置与训练完全一致"——测的是拟合而非泛化 6203、6204 ★★★★
6 传感器噪声缺失：LiDAR 无噪声、事件相机无噪声率/refractory 标定、状态估计直接取真值 6205、6203、6202 ★★★★
7 通信理想化：6202 的 UDR 完全建立在"邻居位置即时可达"上，但未建模丢包/时延/带宽 6202 ★★★★
8 未用 GPU 批量仿真：与 2024+ 主流（Isaac Lab / MJX / Newton）存在代差，视觉输入时吞吐会立刻撞墙 全部 6 个作品 ★★★
9 二维化倾向：6202/6205 的动作与观测都是平面；6203 只有 $[v_x,v_y]$。多旋翼最有价值的 3D 机动被排除 6202、6205、6203 ★★★
10 版本/资产漂移：6201 论文说 UE5，仓库实际是 AirSim 1.8.1（UE4 时代）；复现者会困惑 6201 ★★
问题 1 展开讲：这是"方法论"级别的问题，不是"实验不够"级别 6202 的结论是"UDR 使成功率从 53.3% 提升到 100%"。这个数字是在 Gazebo 里测的，而策略是在 Stage 里训的。于是有两种解释同时存在：
(a) UDR 学到的策略真的泛化到了更真实的动力学；
(b) Stage 的运动学比 Gazebo 更"听话"，任何在 Stage 里学出来的策略到 Gazebo 都会略有退化——UDR 只是退化得少。
区分 (a)(b) 只需要一个实验：把 PPO-LiDAR 与 PPO-UDR 都放到"Stage 版验证场景"里跑一次。如果两者在 Stage 都是 100%，而在 Gazebo 差 47 个百分点，那说明全部差距来自跨域；如果只有 PPO-LiDAR 在 Stage 也差，说明 UDR 确实在解决观测问题。这个实验不需要新代码，只需要把验证场景搬回 Stage——但它没有做。

5.1 各仿真器特定问题清单

Stage

2.5D，只有几何

  • 无姿态动力学、无高度、无气动
  • LiDAR 为理想射线（无噪声/反射率）
  • 与"真机多旋翼"的动力学差距最大
  • 适合验证"几何/拓扑"类结论，不适合验证"控制"类结论
Gazebo + PX4 SITL

高保真但慢，且已 EOL

  • 实时钟约束 → 无法大批量训练
  • 缺风场、气动干扰、地面效应
  • Gazebo Classic 已于 2025-01 EOL，版本组合难复现
  • "高保真"是相对的：接触与传感器模型仍粗糙
AirSim / UE

光度真实，但事件是近似的

  • 事件由"两帧 RGB 差分"生成，本质是帧率采样，仍非真异步
  • AirSim 微软已归档（2022 后维护停滞）
  • 渲染成本高，训练吞吐低
  • 同场景训练/验证 → 泛化未验证
JSBSim

纯动力学，无环境

  • 无风/湍流模型（Dryden 等需自己外挂）
  • 无传感器模型、无视觉
  • 单线程 CPU 积分 → 并行靠进程
  • 机型定制：换飞机要换 xml 并重训
自建 6-DOF

可控但不可复现

  • 无名称、无版本、无代码（6204）
  • 无扰动、无噪声、目标静止
  • 优点是"改 success 判据"极其方便
  • 只适合做"机制验证"，不适合作性能主张
共性缺失

六个作品都没有

  • 域随机化 / 系统辨识
  • sim2sim 同场景对照
  • GPU 批量并行（Isaac/MJX）
  • 风扰、通信退化、感知退化实验
  • 硬件在环（HIL）

6.2 我会在他的栈上加的三件事

  1. 加一张"同场景双仿真器"表：把验证场景同时搬回 Stage 与 Gazebo 各跑 100 次，报「成功率差 / 时间差」。这一个数字能回答"你的结论里有多少是仿真域差异"。成本：1 天；收益：整篇论文的可信度。
  2. 加域随机化：LiDAR 距离噪声 ±2%、邻居位置延迟 50–200 ms、丢包 5–20%、质量/惯量 ±10%。在 Stage 里做最便宜（改几行 env 参数），却能覆盖他所有"通信理想化/无噪声"的缺陷。
  3. 把并行从"进程"升级到"张量"：如果任务仍是低维状态 + 2D LiDAR，用 MJX/MuJoCo Warp 或 Isaac Lab 做 4096 环境并行，把"10 万回合"变成"10 万回合 × 10 分钟"。代价是重写物理，收益是能做真正的超参搜索与多种子统计。

6.3 选型速查（一句话版）

$$ \text{仿真器} = \arg\min\ \{\text{成本}\}\quad \text{s.t.}\quad \text{保真度} \ge \text{观测函数所需的物理} \ \wedge\ \text{吞吐} \ge \text{训练预算所需} $$

这条式子的两个约束都是"下界"而非"越大越好"——这正是他六篇工作共同体现的取舍逻辑：够用就好，多余即浪费。

7.1 一句话定位

他的栈= 2018–2021 年那一代"ROS 原生 + CPU 并行"的 UAV-RL 标准答案 优点是：门槛低、可复现、飞控在环、与真机同构；缺点是：没有 GPU 张量并行、没有可微物理、没有光度真实（除 6203）、没有域随机化。对"写论文、做机制验证"完全够用；对"做产品、追 SOTA 吞吐"已经不够。
