Stack Anatomy · One command, many processes

训练栈不是一个软件，
它是一组契约

“统一”不是把 Gazebo、PX4、YOLO、PPO 编译进同一个可执行文件，而是让它们用同一套数据、同一套时间、同一份场景配置协同工作。 你在终端敲的那一条 ros2 launch 或 Python 脚本，可以启动五个进程，让你感觉像“一个东西”； 但内部仍然是五个各有分工的进程。这不是偷懒，而是因为它们的时间尺度、硬件、保真度、迭代速度根本不同。

一个命令 ≠ 一个进程 接口统一 时间统一 场景统一

00一个命令，五个进程：你现在的栈已经“统一”了

以你的反无任务为例，一个典型的启动脚本实际上做的是：

启动器
ros2 launch / Python orchestrator / docker compose 一份 scenario.yaml
世界与物理
Gazebo Sim：世界、风、地形、相机、intruder 物理
飞控
PX4 SITL defender（advanced_plane） PX4 SITL intruder（x500）
感知
YOLO v11 节点 二阶矩 / 虚拟平面 → 19-D 特征
策略
PPO policy 节点（或外部 trainer）
记录与评估
MCAP / rosbag miss distance / time-to-intercept
关键 用户看到的是“一条命令启动一个系统”；系统内部是“多个进程 + 一组接口”。 统一发生在接口层，不发生在二进制层。

01为什么不能真的塞进一个二进制？

不是不能强行塞，而是塞进去会同时损失性能、可替换性和团队协作。

组件典型频率 / 时间尺度主要硬件保真度重点
物理 / 气动250–1000 HzCPU（或 GPU 批量）接触、气动、积分稳定
PX4 飞控250–400 HzCPU（真实飞控更严格）控制律、延迟、执行器
相机30–60 HzGPU / 图像管线内参、曝光、运动模糊
YOLO20–50 HzGPU检测精度、延迟
PPO 决策10–50 HzGPU（训练） / CPU（推理）样本吞吐、泛化
渲染30–60 Hz（或离线）GPU照片级、材质、光照

1. 时间尺度不同

把 1 kHz 物理、400 Hz 飞控、30 Hz 相机、10 Hz PPO 塞进一个循环，只能按最慢的节拍走，或者写非常复杂的调度。分开进程，各自按自己的频率跑，再用时间戳对齐。

2. 硬件不同

物理和 PX4 吃 CPU 单核/实时性，渲染和 PPO 吃 GPU。一个进程很难同时把 CPU 实时性和 GPU 吞吐都吃满。

3. 保真度重点不同

气动要 JSBSim 级，视觉要 UE/RTX 级，PPO 要万级并行。没有一个引擎能在这三件事上都做到最好；分开才能各取所需。

4. 迭代速度不同

换 reward 不该重编译 Gazebo；换相机不该动 PX4；换气动模型不该动 PPO。接口稳定，组件才能独立演进。

“一个软件”的真相 Isaac Lab 的 isaaclab train、RflySim 的一键启动、AirSim 的 UE 插件，都是把多个模块封装成“一个入口”。 它们内部仍然是物理、渲染、任务、RL 多个子系统。封装让你少配置，不等于单体。

02统一的三个层次：数据、时间、场景

真正要统一的是下面三份“契约”。只要这三份契约稳定，底下换 Gazebo、Isaac Lab、RflySim 都不会把上层推倒重来。

① 数据契约

19-D 观测：7 视觉 + 4 运动学 + 4 姿态 + 3 历史动作 + 1 高度。

动作：acc / pitch / yaw(roll) 的归一化范围、单位、限幅。

坐标系：ENU/NED、机体/世界、相机光学系；时间戳。

② 时间契约

仿真时钟：/clock 或 PX4 sim time；所有节点用同一时间源。

锁步 / 异步：PPO 训练可以锁步；相机、YOLO、PX4 允许有延迟，但必须可测。

延迟：相机曝光、YOLO 推理、MAVLink、舵机，各自打时间戳。

③ 场景契约

一份 YAML：初始位置、速度、航向、风/湍流、相机内参、检测噪声、PPO 配置。

同一份场景在 Gazebo、Isaac Lab、RflySim 里都能加载，才能做 sim2sim。

同一套指标：脱靶量、拦截时间、控制量、漏检率。

契约最小实现常见坑
数据一个 Observation dataclass + JSON schema；训练/推理共用训练用归一化，部署忘了；s1/s2 坐标系和相机系混用
时间ROS 2 /clock + 每条消息带 stamp；记录 latencyGazebo 实时因子波动；PPO 用墙钟，仿真用 sim time
场景一个 scenario.yaml，启动器读取并分发Gazebo 世界文件、PX4 参数、PPO 配置各写一份，改一处忘两处
传输ROS 2 topic（感知/控制）、MAVLink（PX4）、共享内存（高频）ROS 2 与 PX4 时间不同步；高频图像走网络
日志MCAP/rosbag + PPO rollout 日志，统一时间戳失败样本只留在终端，无法回放

03现成工具里，谁最像“一个东西”？

工具你看到的“一个入口”内部实际有什么能否覆盖你的四条链路
Isaac Lab isaaclab train 一条命令 PhysX/Newton + 渲染器 + 任务 manager + RL 库 + 数据管线 气动/PPO/视觉可以，PX4 要外接；固定翼气动要自己补
RflySim 一键启动 PX4 + UE + Simulink PX4 SITL/HITL + UE 渲染 + MATLAB/Simulink + 模型库 最接近全覆盖：固定翼/PX4/视觉；RL 可用 Simulink 或外接 Python
AirSim UE 插件 + Python API UE 渲染 + 简化的多旋翼动力学 + PX4/ArduPilot 接口 视觉强；固定翼弱；RL 要外接
Gazebo + PX4 ros2 launch / PX4 make px4_sitl Gazebo 物理/渲染 + PX4 飞控 + 你的 YOLO/PPO 节点 系统闭环全覆盖；PPO 吞吐弱；视觉中等
JSBSim + FlightGear 两个进程，靠网络/接口连 JSBSim 气动 + FlightGear 渲染/仪表 气动/视觉可以；无 PPO、无 PX4 原生训练
UE5 自定义 一个 UE 工程 渲染 + 场景 + 蓝图/C++；物理和飞控要外接 只覆盖视觉；不是训练栈

结论：RflySim / Isaac Lab 更像“一个软件”，是因为它们把多个模块封装进一个发行版/入口； Gazebo + PX4 更像“一套系统”，因为每个模块都暴露成独立进程。两种都能统一，只是统一在哪一层不同。

04给你的反无栈：一套契约，两种运行模式

不需要把 Gazebo 换掉，也不需要把 PPO 塞进 Gazebo。把栈拆成“训练模式”和“系统模式”，共用同一份 19-D 契约。

共用
scenario.yaml 19-D observation contract action contract metrics
训练模式
Isaac Lab / MuJoCo：固定翼气动 + 特征级观测 + 噪声 PPO GPU 并行 不渲染照片，只生成 19-D 特征
系统模式
Gazebo Sim + PX4：advanced_plane + x500 YOLO + 虚拟平面 PPO 推理节点 MCAP 记录
视觉模式
RflySim / AirSim / UE5：照片级图像 YOLO 训练/验证 不参与 PPO 大规模训练
气动复核
JSBSim / FlightGear：配平、失速、风扰
统一的真正含义 同一份 scenario.yaml、同一个 19-D 定义、同一套指标，能在三种模式里跑。 这样你换仿真器只是换“执行器”，不是重写任务。

05最小统一清单

产物内容放在哪里
scenario.yaml初始位置/速度/航向、风、相机内参、检测噪声、PPO 配置仓库根目录，所有模式读取
observation.py19-D 的字段、顺序、归一化、坐标系、时间戳训练与推理共用同一个包
action.pyacc/pitch/yaw 的范围、限幅、单位、history同上
launchros2 launch / docker compose / Python orchestrator一条命令启动系统模式
recorderMCAP/rosbag + PPO rollout + 指标统一时间戳，能回放失败
evalmiss distance、time-to-intercept、控制量、漏检率三种模式共用

06什么时候可以“只用一个软件”？

可以

  • 任务简单、只做刚体控制，不需要 PX4/HIL
  • 团队小，接受用一个发行版绑定物理+渲染+RL
  • 只需要一种保真度（比如纯视觉或纯控制）
  • 用 Isaac Lab / RflySim 的封装入口，接受它的边界

不建议

  • 同时要固定翼气动、照片级视觉、PX4 HIL、GPU 大规模 PPO
  • 需要换物理引擎或换渲染器做 sim2sim
  • 多人分工：气动、感知、RL、飞控各管一摊
  • 需要把真机失败样本回放到仿真里
一句话 统一的是契约，不是二进制。一个命令可以启动五个进程；五个进程可以像一件事一样工作。
